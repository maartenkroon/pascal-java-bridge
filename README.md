# pascal-java-bridge

Call Java from Object Pascal (Free Pascal and Delphi) through generated, reference-counted
wrapper interfaces, and implement Java interfaces in Pascal (callbacks). The JVM runs
**inside** the Pascal process (JNI Invocation API). On a modern x86-64 machine a Pascal→Java
call costs about 75 ns and a Java→Pascal callback about 335 ns.

```pascal
JavaStartVM('', ['-Djava.class.path=myapp.jar']);   // libjvm from JAVA_HOME

L := TJArrayList.New;                 // constructor
L.add(TJStringBuilder.New('hello'));  // instance method
WriteLn(L.get(0).toString);           // returned objects are wrapped automatically
WriteLn(TJInteger.MAX_VALUE);         // static field
// no Free needed: wrappers are interfaces, the Java object is released with the last reference
```

## Layout

A Maven multi-module project (JDK 17+ to run the generator, built and tested with JDK 25):

| Path | What |
|---|---|
| `runtime/JavaBridge.pas` | Runtime unit: JVM start/attach, JNI helpers, `TJavaObjectImpl`, exceptions, callbacks |
| `runtime/JavaBridgeHandler.inc` | Embedded bytecode of the callback handler (written by the `handler` module) |
| `runtime/JavaBridgeCom.pas` | Delphi only: late-bound COM Automation (`IDispatch`) access to Java objects |
| `runtime/JavaBridgeDynamic.inc` | Embedded bytecode of `DynamicInvoker`, the Java side of `JavaBridgeCom` |
| `handler/` | `PascalInvocationHandler` (Java side of callbacks), `DynamicInvoker` (Java side of COM), and the tool that writes the `.inc` files |
| `generator/` | `BindingGenerator`: executable jar, also contains the Pascal runtime |
| `maven-plugin/` | `pascal-java-bridge:generate` goal for use in Maven projects |
| `tests/` | Java test classes (`Torture`: naming collisions, `CallbackHost`: callbacks), `JDemo` generated by the plugin (as one unit and as one unit per package), Pascal test programs `src/test/pascal/TestBindings.pas` and (Delphi) `TestCom.pas` |
| `comserver/PascalJavaBridgeCom.dpr` | Delphi in-process COM server (ProgID `PascalJavaBridge.JVM`) over `JavaBridgeCom` |
| `examples/RawJniDemo.pas` | The original hand-written JNI demo (raw JNI, no generator) |
| `build.sh` | Shortcut for `mvn verify` with the Pascal tests (uses `$FPC` or `fpc` on the `PATH`) |

## Building

```bash
mvn verify                                   # Java modules only
mvn verify -Dfpc.executable=/path/to/fpc     # also compile and run the Pascal tests
mvn verify -Ddcc.executable=dcc64            # the same with Delphi (Windows)
mvn install                                  # put the generator and plugin in ~/.m2
```

With `-Dfpc.executable`, the `tests` module:
1. generates `JDemo.pas` with the plugin;
2. compiles `TestBindings.pas` with `-Sew` (warnings are errors);
3. runs it under `-Xcheck:jni`, with `JAVA_HOME` set to the JDK running Maven.

With `-Ddcc.executable` (profile `delphi-tests`) it does the same with Delphi, in
`tests/target/delphi` (warnings are not errors there), and also compiles and runs `TestCom.pas`
(the COM late binding) and builds the COM server DLL. Add `-Dcom.scripts` to also test the DLL
from VBScript, JScript and PowerShell (`src/test/script`). That registers it for the current
user and unregisters it again. Both properties can be set in one build.

A failing test fails the build. Use `-DskipTests` to compile without running.

**Eclipse**: the project imports as a normal Maven project. Eclipse's Maven integration (m2e)
cannot resolve a Maven plugin that is built in the same workspace. So inside Eclipse the
`tests` module skips the plugin (profile `generate-pascal`, active only when `m2e.version` is
not set), and the `handler` module doesn't rewrite the `.inc` files. Run `./build.sh` or
`mvn verify` on the command line for those steps.

The `handler` module rewrites `runtime/JavaBridgeHandler.inc` and `runtime/JavaBridgeDynamic.inc`
when their bytecode changes. Commit both, so people who use the Pascal sources without Maven get
them too.

## Generating bindings

### With Maven

```xml
<plugin>
  <groupId>io.github.maartenkroon</groupId>
  <artifactId>pascal-java-bridge-maven-plugin</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <executions>
    <execution>
      <goals><goal>generate</goal></goals>
      <configuration>
        <unit>MyJava</unit>
        <includes>
          <include>com.example.**</include>
          <include>java.util.ArrayList</include>
        </includes>
        <excludes>
          <exclude>com.example.internal.**</exclude>
        </excludes>
      </configuration>
    </execution>
  </executions>
</plugin>
```

The goal runs in the `process-classes` phase. Its classpath is the project's own classes plus
its runtime dependencies, so nothing has to be listed by hand.

| Parameter | Default | |
|---|---|---|
| `unit` | (required) | Pascal unit name (`-Dpascal.unit`) |
| `includes` | (required) | class names or patterns, see below |
| `excludes` | | patterns to leave out |
| `depth` | `0` | also wrap referenced types, n levels deep |
| `outputDirectory` | `target/generated-sources/pascal` | |
| `withRuntime` | `true` | also write the runtime there (`JavaBridge.pas`, `JavaBridgeCom.pas` and their `.inc` files) |
| `unitPerPackage` | `false` | one unit per Java package, see [Large selections](#large-selections-one-unit-per-package) (`-Dpascal.unitPerPackage`) |
| `skip` | `false` | `-Dpascal.skip` |

### From the command line

```bash
java -jar generator/target/pascal-java-bridge-generator-0.1.0-SNAPSHOT.jar \
     --unit MyJava --out src --cp myapp.jar --with-runtime \
     'com.example.**' --exclude 'com.example.internal.**' java.util.ArrayList 'java.util.Map$Entry'
```

Arguments are class names or wildcard patterns (quote them so the shell doesn't expand `*`):

| Pattern | Selects |
|---|---|
| `java.util.ArrayList` | one class; nested classes use the binary name: `java.util.Map$Entry` |
| `java.util.*` | all public classes and interfaces in package `java.util` (including public nested ones) |
| `java.util.**` | the same for `java.util` and all its subpackages |
| `java.util.*Map` | `*` matches within one name segment (no `.`) |
| `java.**.spi.*` | `**` matches across packages |

* Wildcards search the JDK's modules and every directory or jar on `--cp`. For JDK modules,
  only packages the module exports are included (no `sun.*` / `jdk.internal.*`
  implementation classes).
* A class that can't be loaded or inspected (e.g. a jar whose dependencies are missing) is
  skipped with a warning. For an explicitly named class, that's an error instead.
* `--exclude <pattern>` (repeatable, same syntax) removes classes from the selection,
  including from those added by `--depth`.
* `--depth n` also wraps the public types referenced by the selected classes, `n` levels deep.
* `--unit` sets the name of the Pascal unit (written to `<out>/<unit>.pas`); `--cp` is the
  classpath used to load the classes. JDK classes are always available.
* `--with-runtime` also writes the runtime (`JavaBridge.pas`, `JavaBridgeCom.pas` and their `.inc`
  files) to `--out`.
* `--unit-per-package` splits the output into one unit per Java package (see below).

`java.lang.Object` is always included. Types that are not wrapped show up as `IJavaObject`;
add them to the selection to get typed wrappers.

### Large selections: one unit per package

Generated code grows by roughly 200 lines per Java type. `java.util.**` gives 386 types and
90k lines in one unit, and FPC compiles it in about 1 s. However, **FPC 3.2.2 crashes with an
internal error** ("Compilation raised exception internally", `EListError: List index exceeds
bounds (-1)`) on very large units, e.g. `java.**` in one unit (2,110 types, 430k lines). It is
a compiler bug, not invalid code.

For selections like that, use `--unit-per-package` (Maven: `<unitPerPackage>true</unitPerPackage>`).
The output is then split:

| Unit | Contents |
|---|---|
| `<unit>` (e.g. `JJava`) | all interface types (`IJFoo`, `IJFooCallback`) |
| `<unit>_<package>` (e.g. `JJava_java_util`) | the records (`TJFoo`) and implementation classes of one package |

```pascal
uses
  JavaBridge, JJava, JJava_java_util, JJava_java_time;
```

Pascal does not allow circular references between the interface sections of units, so packages whose
classes inherit from each other in a cycle share a unit; the generator prints a warning when
that happens. With `java.**`, `java.lang`, `java.io`, `java.lang.annotation`,
`java.lang.constant`, `java.security`, `java.util` and `java.util.function` end up in
`JJava_java_lang` (for example `java.lang.RuntimePermission` extends
`java.security.BasicPermission`, which extends `java.lang.Object`); the header of each unit
lists its packages and types. All of `java.**` (67 units) then compiles in about 7 s.

Names, GUIDs and behaviour are the same in both modes, so switching only changes the `uses`
clauses. Files of packages that are no longer selected are not deleted; clean the output
directory when you shrink the selection.

## What gets generated

For each Java type `Foo`:

| Pascal | Contents |
|---|---|
| `IJFoo` (interface) | public instance methods, getters/setters for public instance fields |
| `TJFoo` (record) | `New(...)` constructors, static methods, static field getters/setters, `Cast`, `IsInstance` |
| `TJFooImpl` | implementation class (internal; in the implementation section, or the package unit's interface section with `--unit-per-package`) |

For each Java **interface** `Foo` with abstract methods, there are two more:

| Pascal | Contents |
|---|---|
| `IJFooCallback` (interface) | the abstract methods of `Foo`, to implement in a Pascal class |
| `TJFoo.Implement(cb)` | wraps a Pascal `IJFooCallback` in a Java object implementing `Foo` |

`IJFoo` inherits from the interface of the nearest wrapped Java superclass (for Java
interfaces: the first wrapped super-interface), ending in `IJObject` → `IJavaObject`. Other
interfaces that a Java class implements are reached with a checked cast:
`TJRunnable.Cast(Obj).run`.

### Type mapping

| Java | Pascal |
|---|---|
| `boolean byte char short int long float double` | `Boolean ShortInt WideChar SmallInt Integer Int64 Single Double` |
| `String` | `UnicodeString` (UTF-16 copy; Java `null` becomes `''`) |
| `Object` parameter | `IJavaObject` (accepts any wrapper) |
| `Object` result | `IJObject` |
| wrapped type `Foo` | `IJFoo` |
| other reference types | `IJavaObject` |
| `int[]`, … | `TJavaIntArray`, … (copied) |
| `String[]` | `TJavaStringArray` |
| other arrays | `TJavaObjectArray` (elements are `IJavaObject`) |
| `void` | procedure |

Generics are erased, as in the JVM: `List<String>.get` returns `IJObject`.

## Name collisions

The generator guarantees that the generated unit compiles and that no Java name can shadow
anything the generated code relies on:

* **Pascal keywords and directives** (`type`, `begin`, `end`, `read`, `index`, `string`, …) are
  escaped with `&`: `Obj.&type`.
* **Case-insensitivity**: all scopes compare names case-insensitively. When two Java names differ
  only in case (`getURL` / `getUrl`), the second one gets a suffix: `getUrl_1`.
* **Overloads** stay overloads. If two Java overloads map to the same Pascal parameter types
  (e.g. two unwrapped classes, both `IJavaObject`), the later one is renamed (`foo_1`).
* **Inherited members** keep the name they got in the ancestor; an overload added in a subclass
  joins the ancestor's name.
* **TObject / TInterfacedObject members** (`Destroy`, `Free`, `ClassName`, `ToString`, `RefCount`,
  …) are safe to use as Java method names. The implementation class only has mangled methods
  (`J_17`), which method-resolution clauses bind to the interface methods. Delphi can't bind
  overloaded interface methods with a clause, so under Delphi the implementation class gets
  `reintroduce; overload;` forwarders named after the overloaded interface methods. The runtime
  members the generated code calls (`JavaGlobalRef`, `CreateFromLocal`, `CreateFromGlobal`)
  are therefore never overloaded: a second overload of a Java method with such a name is
  renamed (`JavaGlobalRef_1`).
* **Reserved names** are renamed with a `_n` suffix:
  * `QueryInterface`, `_AddRef`, `_Release`, `Self`, `Result`
  * Pascal type names used in signatures (`Integer`, `UnicodeString`, …)
  * every identifier exported by `JavaBridge`
  * the generated type names
  * the local variable names used in generated bodies

  Example: Java `self()` becomes `self_1`.
* **Fields vs. methods**: a field getter never shares a name with a method. If a class has both a
  method `counter()` and a field `counter`, the method keeps the name and the getter becomes
  `counter_1`. Setters are `Set_<name>`.
* **Constructors** are `New`; a static Java method named `New` / `cast` / `isInstance` is renamed.
* **Type names**: the simple class name is used; when two wrapped classes share a simple name,
  both use the qualified name (`IJjava_util_List`, `IJjava_awt_List`). Every generated type
  name starts with `IJ` or `TJ`.
* **Parameters** are named `p0, p1, …`; if a member is called `p0`, parameters become `p_0, …`.
* **Non-ASCII identifiers** are mangled (`café` → `caf_u00E9`).

The interface declarations carry a comment with the original Java name and JNI signature
of each member, so renamed members are easy to find.

## Callbacks (Java → Pascal)

Implement the generated `...Callback` interface in an ordinary Pascal class and pass the
object to `Implement`. You get back a normal wrapper that you can hand to any Java API:

```pascal
type
  TByLength = class(TInterfacedObject, IJComparatorCallback)
    function compare(const p0, p1: IJObject): Integer;
  end;

function TByLength.compare(const p0, p1: IJObject): Integer;
begin
  Result := Length(p0.toString) - Length(p1.toString);
end;

List.sort(TJComparator.Implement(TByLength.Create));       // java.util.Comparator
Host.addListener(TJCallbackHost_Listener.Implement(MyListener));
TJCallbackHost.runInThread(TJRunnable.Implement(MyRunnable));
```

* **How it works**: `Implement` creates a `java.lang.reflect.Proxy`. Its handler class
  (`pascaljavabridge.internal.PascalInvocationHandler`) is embedded in `JavaBridge` as bytecode. It is
  defined in the system class loader on first use and calls two native methods implemented in
  Pascal (registered with `RegisterNatives`). You don't need a jar or a native library.
* **Types are mirrored**:
  * callback parameters use the *result* mapping (Java `Object` arrives as `IJObject`)
  * callback results use the *parameter* mapping (return any wrapper as `IJavaObject`)
  * primitives are boxed and unboxed automatically
* **Default methods** are not in the callback interface; they run their Java implementation.
  `equals`/`hashCode`/`toString` of the proxy use identity semantics.
* **Exceptions**:
  * A Pascal exception escaping a callback becomes a `java.lang.RuntimeException` with the
    message `EClassName: message`.
  * An `EJavaException` (a Java exception that passed through Pascal) is rethrown as the
    original Java exception.
  * Nothing ever unwinds through JVM frames.
* **Threads**: Java may call a callback on any thread, including threads that Java created.
  The callback runs on that thread; with FPC on Unix, `cthreads` must be in the program.
* **Lifetime**: Java holds a reference to the Pascal object until the proxy is garbage
  collected. The release then happens on Java's `Cleaner` thread, so the destructor of your
  callback class may run on that thread. `JavaCallbackCount` tells how many are alive.
  A Pascal variable, or a hidden temporary, holding the returned wrapper keeps the proxy
  reachable.
* **Classes implementing Java interfaces**: a wrapper of a Java class doesn't inherit the
  interfaces of the Java interfaces it implements. Use a checked cast:
  `TJList.Cast(MyArrayList)`.
* **Method names in your class**: callback methods carry the same (possibly escaped or renamed)
  names as in `IJFoo`. If one of them clashes with a member of your own class (e.g. a Java
  method `Destroy`), use a method resolution clause:
  `procedure IJFooCallback.Destroy = JavaDestroy;`.

## COM Automation, late binding (Delphi)

`runtime/JavaBridgeCom.pas` (Delphi on Windows only) gives COM clients `IDispatch` access to any
Java object by member name. It needs no generated code and no type library. The design and the
next steps are in [docs/com-automation.md](docs/com-automation.md).

**COM server**: `comserver/PascalJavaBridgeCom.dpr` builds an in-process server DLL with one
class, ProgID `PascalJavaBridge.JVM` (threading model `Both`). Build and register it:

```
dcc64 -NSSystem -Uruntime -Iruntime comserver\PascalJavaBridgeCom.dpr
regsvr32 /n /i:user PascalJavaBridgeCom.dll     # current user; plain regsvr32 (elevated): all users
regsvr32 /u /n /i:user PascalJavaBridgeCom.dll  # unregister
```

Then, from VBScript (`cscript`), VBA or any other Automation client:

```vb
Set jvm = CreateObject("PascalJavaBridge.JVM")
jvm.Start "myapp.jar"                      ' JAVA_HOME must point to the JDK, or set jvm.JvmPath
Set list = jvm.New("java.util.ArrayList")
list.add 42
MsgBox list.size & " " & jvm.Static("java.lang.Math").max(1, 2)
For Each item In list : WScript.Echo item : Next
```

The JVM runs inside the client process, so it must have the client's bitness: 64-bit `cscript`
or Office needs a 64-bit JDK and a dcc64 build, 32-bit ones need dcc32 and a 32-bit JDK. There is
one JVM per process, and the DLL stays loaded once it is loaded. **PowerShell** binds COM
properties only through type info, which this server doesn't have. Read properties and fields as
methods (`$jvm.Running()`, `$jvm.Static("java.lang.Integer").MAX_VALUE()`) and set the JVM path
with `$jvm.JvmPath("...")`. Method calls work as usual.

From Delphi, without registration:

```pascal
uses JavaBridgeCom;
var
  JVM, List: OleVariant;
begin
  JVM := JavaComJVM;                         // the entry object
  JVM.Start('myapp.jar', VarArrayOf(['-Xmx512m']));
  List := JVM.New('java.util.ArrayList');
  List.add(42);
  WriteLn(List.size, ' ', JVM.Static('java.lang.Math').max(1, 2));
end;
```

Entry object members:

| Member | What |
|---|---|
| `Start(classPath [, option...])` | starts the JVM; options may also be arrays. `False` if it was already running |
| `Running` | whether the JVM runs |
| `JvmPath` | `jvm.dll` to load (read/write); default: from `JAVA_HOME` |
| `New(className [, arg...])` | creates an object, choosing the constructor from the arguments |
| `Static(className)` | the static methods and fields of a class |
| `Cast(obj, className)` | `obj`, showing only the members of `className` (checked) |
| `Implement(interfaceName, comObject)` | a Java proxy that calls the COM object's methods by name |

`New`, `Static` and `Implement` start the JVM without options if `Start` wasn't called.

How calls work:

* **Members**: public methods and fields of the object's class and of all its public supertypes,
  looked up case-insensitively (an exact-case match wins). `obj.Name` also finds `getName()`,
  `isName()` and `setName(x)`. When a public field and a no-argument method have the same name,
  reading it as a property gets the field.
* **Overloads** are chosen at run time from the argument values: exact types first, then
  widening, then narrowing that fits (an `Integer` for a `short`, a whole `Double` such as an
  Excel cell value for an `int`), a one-character string for a `char`. Varargs work.
* **Arguments**: integers become `Integer` (or `Long`), `Single`/`Double` become `Float`/`Double`,
  `Currency`/`Date`/`Decimal` become `Double`, strings become `String`, `Null`/`Empty` becomes
  `null`, 1- and 2-dimensional variant arrays become `Object[]` (or `Object[][]`) and are
  converted to the parameter's array type. Java objects (`TJavaDispatch`) pass through. Other
  COM objects must be wrapped with `Implement`.
* **Results**: `null` is `Null`; `boolean` is `Boolean`; `byte`/`short`/`int` are `Integer`;
  `long` is `Integer` when it fits, else `Int64` (VBScript has no `Int64`); `float`/`double`
  are `Single`/`Double`; `char`/`String` are `BSTR`; arrays are variant arrays; any other object
  is a new `TJavaDispatch`.
* **Default member** (`DISPID_VALUE`): `obj(i)` calls `get(i)`, `obj(i) = x` calls `set(i, x)`,
  and `obj` on its own is `toString()`. **For Each** works on an `Iterable`, `Iterator`,
  `Enumeration`, `Map` (its entries) or array.
* **Exceptions**: a Java exception becomes a COM exception (`DISP_E_EXCEPTION`). Its source is
  the Java class name and its description is the message. Delphi raises `EOleException`.
* **Callbacks**: `Implement` calls the COM object's method with the Java method's name. If the
  object has no such method (a VBScript `GetRef`), or is a JScript function (it has `call` and
  `apply`), it calls the object's default member. The result is converted to the Java return
  type.
* **Threads**: Java objects can be called from any thread. A COM object passed to `Implement` is
  only called on the thread that passed it. A call from another Java thread throws a
  `RuntimeException` in Java. When Java garbage-collects the proxy, the COM object is released on
  its own thread, during that thread's next call into `JavaBridgeCom`. `JavaComReleasePending`
  does this explicitly.

`TJavaDispatch.Create(obj)` wraps an existing `IJavaObject` (such as a generated wrapper) for COM,
and `JavaToVariant` / `JavaFromVariant` do the conversions above.

## Runtime notes

* **FPU exceptions**: the JVM requires masked floating point exceptions. `JavaStartVM` masks
  them on every thread that calls Java (pass `MaskFPUExceptions = False` to opt out). As a
  result, Pascal code on those threads gets `Inf`/`NaN` instead of `EDivByZero` etc.
* **Threads**: threads are attached to the JVM automatically, as daemon threads, on their first
  Java call. Call `JavaDetachThread` before a thread ends. With FPC on Unix, put `cthreads`
  first in the program's `uses` clause.
* **Exceptions**: a Java exception becomes `EJavaException`, with `JavaClassName`, `Message`
  (`Throwable.toString()`) and `Throwable` (an `IJavaObject`; cast it with a generated wrapper).
  If a class or method can't be found, you get `EJavaError`; a failed `Cast` gives
  `EJavaCastError`.
* **Identity**: two wrappers can refer to the same Java object; use `JavaSameObject(A, B)`
  (Java `==`) or `A.equals(B)`.
* **Shutdown**: `JavaStopVM` destroys the JVM. Wrappers that are released afterwards don't
  touch the JVM. HotSpot cannot be restarted in the same process.
* **Signals**: the JVM uses `SIGSEGV` internally and chains to handlers installed *before* it
  started. That includes FPC's, so nothing is needed by default. If you install signal handlers
  after `JavaStartVM`, run with `LD_PRELOAD=$JAVA_HOME/lib/libjsig.so`.
* **Native library mode**: if the Pascal code is a library loaded by Java, call
  `JavaUseVM(vm)` from `JNI_OnLoad` instead of `JavaStartVM`.

## Status and limitations

* Tested with **FPC 3.2** on Linux x86-64 and **JDK 25**:
  * 75 tests pass, including with `-Xcheck:jni`, for both the single unit and one unit per package
  * all of `java.**` (2,110 types, one unit per package) compiles
  * a 123-type JDK binding (42k lines, 67 callback interfaces) compiles without warnings
* Tested with **Delphi 11** (dcc64) on Windows x64 and **JDK 25**: the same 75 tests pass, with
  `-Xcheck:jni`, in both layouts. The test program also compiles with dcc32 (not run: no
  32-bit JVM). Run them with `mvn verify -Ddcc.executable=dcc64` (profile `delphi-tests`).
  That profile also runs `TestCom` (65 tests of the COM late binding, under `-Xcheck:jni`).
  With `-Dcom.scripts`, the COM server passes its VBScript (20), JScript (7) and PowerShell (8)
  tests.
  FPC on Windows has not been tested.
* Callbacks can implement Java **interfaces** only, not abstract classes
  (`java.lang.reflect.Proxy` cannot extend classes).
* A callback call (about 335 ns) goes through `Proxy` plus boxing. Generating a dedicated Java
  class per interface could bring it closer to the Pascal→Java cost.
* Static methods are taken from the class that declares them only: call
  `TJParent.staticMethod`, not `TJChild.staticMethod`.
